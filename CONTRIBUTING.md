# Contributing

Thanks for wanting to contribute to the project!

## Getting Started

- Ensure you have the LTS version of Node.js installed (see https://nodejs.org/en/)
- Ensure if you are using Windows to use the Windows Subsystem for Linux (WSL)
- Run `yarn install` in the root of the project to install all dependencies
- Please be respectful when communicating within the project

### Creating a new component

These are the steps to follow when creating a new component:

1. Create a new folder in `packages/components` with the name of your component

2. Add the following files in the new folder:

   - `package.json`
   - `src/index.ts`
   - `src/register.ts`
   - `src/<component-name>.ts`
   - `src/<component-name>.css`
   - `src/<component-name>.spec.ts`

   When in doubt, copy the files from an existing component and rename accordingly.

   All source code lives in `src`; `package.json` is the only file in the root of the package. Components do not have their own TypeScript, ESLint or stylelint configuration: `packages/components/tsconfig.json`, `packages/components/eslint.config.mjs` and `packages/components/stylelint.config.mjs` cover every component in the monorepo.

3. Run `yarn install` in the root of the project, so yarn picks up the new workspace. The root `package.json` includes `packages/components/*`, so there is nothing else to register anywhere.

4. Add a `src/<component-name>.stories.ts` file and start writing Storybook stories

5. Add a `src/<component-name>.spec.ts` file and start writing unit tests; see [Tests](#tests) for how to run them

6. Run `yarn start` in the root of the project to start Storybook

7. Start developing your new component!

### Package configuration

The `exports` field and the `publishConfig.exports` field in `package.json` are **generated by tsdown** while building; do not edit them by hand. During development, `exports` points at the TypeScript sources in `src`, while `publishConfig.exports` points at the built output in `dist` that is used when the package is published.

By default every package is built with `src/index.ts` and `src/register.ts` as entry points. If your component needs additional entry points (a separate utility module for example), add a `tsdown` field to its `package.json` listing all of them:

```json
"tsdown": {
  "entry": ["src/index.ts", "src/register.ts", "src/utils.ts"]
}
```

Run `yarn build` afterwards to regenerate the exports and commit the result.

### Styles

Component styles are written in plain CSS in `src/<component-name>.css` and imported as a constructable stylesheet using an import attribute:

```ts
import styles from './my-component.css' with { type: 'css' };

export class MyComponent extends LitElement {
  static override styles: CSSResultGroup = styles;
}
```

The `with { type: 'css' }` attribute is handled by the `@sl-design-system/rolldown-plugin-css-sheet` plugin, which is configured for tsdown, Vitest and Storybook alike. CSS imports without the attribute are left untouched.

## Building

The packages are built with [tsdown](https://tsdown.dev). Run `yarn build` in the root of the project to build everything (components, examples, locales and themes). This also generates the type declarations and updates the `exports` fields in the various `package.json` files.

You do not need to run the build while developing: Storybook and the tests consume the TypeScript sources directly.

If you want to build the components only, you can run tsdown directly:

```bash
yarn tsdown --config packages/components/tsdown.config.mjs
```

Add `--filter <package-name>` to build a single package, or `--watch` to rebuild on every change.

## Naming

This is an international project and as such everything uses the American English language.

When writing code in this project, please follow the following naming conventions:

- For NPM packages, we use the `sl-design-system` organization with component name for the actual packages; for example: `@sl-design-system/button`
- For web components, we use the `sl-` prefix; for example: `<sl-button>`
- All web component events use the `sl-` prefix and "dasherize" convention; for example: `sl-active-item-change`

## Branching

The main branch of the repository is called `main`. All releases are done from this branch automatically using GitHub Actions and `changesets`. If you want to work on something, please create a new branch from `main`.

When creating a branch, please prefix the branch with the type of thing you intend to work on:

- `chore/update-dependencies`
- `docs/improve-button`
- `feature/my-cool-component`
- `fix/dialog-close-button`

When you finish the branch and want to get your changes merged into `main`, please create a Pull Request. After your PR has been reviewed & approved, your commits will be squashed and merged in `main` as a single commit.

When you create a PR, please make sure the PR is associated with the issue. You can do this by either typing "Fixes #123" in the body of the PR, or by manually associating an issue with a PR.

Please run `yarn changeset` locally to create an entry for `CHANGELOG.md` (note that this is not needed when you make changes to the website only).

## Linting

Linting is done using `eslint` for TypeScript and `stylelint` for CSS. Both are setup in a such a way that they should work automatically if you are using Visual Studio Code (see the recommended extensions in `.vscode/extensions.json`). If you are using a different development environment, it is up to you to correctly setup integration. To lint everything from the command line, run `yarn lint` in the root of the project.

As part of linting, `oxfmt` also runs every time you save a file in vscode. This will format your code according to the project standards.

Using `husky`, whenever you create a new git commit, `lint-staged` will check if all the staged code passes the linting checks. If not, then the commit will fail. Fix the errors and try again.

## Tests

Tests are written with [Vitest](https://vitest.dev) and run in a real browser using Playwright. To run all the tests in the project, simply run `yarn test` from the project root.

If you want to run the tests while developing, run Vitest in watch mode from the project root and pass the path of the package you are working on:

```bash
yarn vitest --project=unit packages/components/button
```

This will automatically rerun the tests for that package whenever you update a file.

When you create/update a web component, please also create/update the associated unit tests.

## Documentation

In code documentation is used for the Design System website. To make sure the information is consistent we have some style guidelines for the code comments:

- Start sentences with a capital, end with a period.
- Use "The `property` of the `component`." to describe simple properties that are used to provide options (color, style, width etc.).
- Use "Whether the `component` is `property`." to describe states of the component that can be set (checked, invalid, readonly etc.).
- No need do mention what the default value is; that is apparent from other parts of the documentation website.

- Slots are defined at the top of the file, just above the class declaration, using `@slot <slot name> - Description`
