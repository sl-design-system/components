# HTML as the deliverable, and what that fixes

The output is three HTML files generated by script, with verifiable contracts. Framework code
comes later, from the HTML rather than from Figma.

This was in the plans as a mention — `draft-measurement-method.md` names "the overlay viewer's
anchors" as one of three things `data-figma-node` delivers — but never as a position. It deserves
to be one, because it resolves a problem the earlier framing could not.

---

## The deliverables

|     | File                        | Generated from                   | Purpose                                                       |
| --- | --------------------------- | -------------------------------- | ------------------------------------------------------------- |
| 2.1 | **the design**              | captures                         | renders as the Figma does                                     |
| 2.2 | **the overlay**             | the design + the decision record | marks what matched and what did not, per element, inspectable |
| 2.3 | **the progress** (optional) | the run record                   | what the run did, where it is                                 |

All three by script. Contracts on the inputs, validated — the index and the run record are ours
and can carry a schema; the captures stay raw, because the protocol's rule that a capture file
holds exactly what the call returned is what makes it re-readable when a reader turns out to be
wrong.

## Why this is better than what I proposed, and not a smaller version of it

I had the two stakeholder goals being satisfied by **two readings of one artifact**. Putting HTML
first satisfies them at **two different stages**, which is stronger:

| Goal                                                     | Satisfied by                                               | Why it holds                                                                                                                           |
| -------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| design system team — faithful, repeatable, ideally exact | **2.1, script-generated**                                  | a script has no judgement, so two runs of one design produce byte-identical output. **Determinism by construction, not by discipline** |
| competence owner — useful in real projects               | the framework code, generated later from the HTML contract | agent judgement lives here, where a human reviews a PR anyway                                                                          |

The variance the control measured — three of nineteen cases flipping outcome because one analyst
decided differently from another — **cannot occur in a script-generated artifact.** Moving the
deliverable to a point before agent judgement enters is the single largest determinism win
available, and it is free in the sense that the work was going to be done anyway.

## What can be a script, and what genuinely cannot

Worth being exact, because "minimise the agent" is only useful if the line is drawn somewhere
defensible.

**Script, no agent, no ambiguity:**

- **mode decision** — call, write, grep for `sl-*` in external dependencies, classify. Probed; the
  discriminator is mechanical
- **traversal** — the capture protocol's depth rules are already an algorithm: metadata at the
  root, `get_design_context` on each child frame or instance over ~100px, recurse where the
  response has no `data-node-id` below its root, **stop at a `CodeConnectSnippet` reference**
- **classification of unresolved nodes** — suggestions call, drop descendants of resolved
  instances, drop assets, sort into the five causes. Needs the resolved set and parentage; both
  are on disk
- **every check** — reconstruction, text coverage, cross-source agreement, token existence, type
  check, render verdict. Three already exist
- **all three HTML files**

**Agent, because it is judgement:**

- what becomes a component, and what it is called
- inferring an SLDS component for an unmapped Figma one — the `inferred` basis, by definition a
  guess
- the twenty to thirty open questions per screen
- writing the framework implementation

So the agent's job shrinks to: _given a captured, verified, classified structure, decide what is a
component and write it._ Everything before that is deterministic, and **everything before that is
where the measured variance was.**

## The overlay, specifically

Per element, anchored on `data-figma-node`:

- a state — matched, approximated, inferred, invented, missing
- on hover or click: what the design said, what was emitted, the delta, the basis, and the cause
  if unresolved
- colour by state, so the shape of the problem is visible before anything is read

This is the thing that makes "no decisions handed to humans" work. A human is not asked to resolve
an element; they **look at a page and see where the run was unsure**. Aggregated across a corpus
it becomes the per-pattern question — _these nine tokens never reach their designs, which do you
want?_ — rather than a per-element queue.

It also needs nothing new: the state comes from `decisions.jsonl`, the anchor from
`data-figma-node`, and the geometry is already in the design HTML.

## The open question this does not settle, and the cheapest way to settle it

**Can a script produce 2.1 faithfully?** `render-design.mjs` exists and converts captures to HTML,
but its own header is explicit: _"a completeness probe, not a fidelity target… it will never match
the reference pixel for pixel — text layout, font metrics and effects are not reproducible this
way — so it must never be scored against the PNG."_

That is a statement about the current converter, not a proof about the data. `get_design_context`
returns resolved values inline, which is the hard part. Whether what it returns is **enough for
visual fidelity** has never been tested, because the probe was never meant to be.

**The experiment is cheap and comes before everything else in the plan.** Take one well-captured
run, render it, compare to the reference, and measure how far off it is and in what. If the gap is
small the HTML-first position is sound. If the gap is large and structural, 2.1 needs more than
the captures hold, and that changes what Phase 1 must collect — which is much better learned now
than after the registry is keyed.

Call it **T0**: cheaper than T1, and it tests the premise everything else rests on.

## What this does to "our metadata"

The instinct was right and the artifact is thinner than it sounded. There is **no transformation
of Figma's output into a common format** — transforming raw output loses fidelity and adds a place
to be wrong, and `get_design_context` already emits structured JSX with `data-node-id` on every
element.

What is ours, and what carries a validated schema:

- **capture index** — what was fetched, by which call, truncated or not (exists)
- **run record** — what was decided, append-only
- **decision record** — per element: source, emitted, basis, delta

The captures stay raw. The schema sits on the records that describe them, not on the bytes.
