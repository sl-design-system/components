# HTML as the deliverable, and what that fixes

The output is three HTML files generated by script, with verifiable contracts. Framework code
comes later, from the HTML rather than from Figma.

This was in the plans as a mention — `draft-measurement-method.md` names "the overlay viewer's
anchors" as one of three things `data-figma-node` delivers — but never as a position. It deserves
to be one, because it resolves a problem the earlier framing could not.

---

## The deliverables

|     | File                        | Generated from                   | Purpose                                                       |
| --- | --------------------------- | -------------------------------- | ------------------------------------------------------------- |
| 2.1 | **the design**              | captures                         | renders as the Figma does                                     |
| 2.2 | **the overlay**             | the design + the decision record | marks what matched and what did not, per element, inspectable |
| 2.3 | **the progress** (optional) | the run record                   | what the run did, where it is                                 |

All three by script. Contracts on the inputs, validated — the index and the run record are ours
and can carry a schema; the captures stay raw, because the protocol's rule that a capture file
holds exactly what the call returned is what makes it re-readable when a reader turns out to be
wrong.

## Why this is better than what I proposed, and not a smaller version of it

I had the two stakeholder goals being satisfied by **two readings of one artifact**. Putting HTML
first satisfies them at **two different stages**, which is stronger:

| Goal                                                     | Satisfied by                                               | Why it holds                                                                                                                           |
| -------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| design system team — faithful, repeatable, ideally exact | **2.1, script-generated**                                  | a script has no judgement, so two runs of one design produce byte-identical output. **Determinism by construction, not by discipline** |
| competence owner — useful in real projects               | the framework code, generated later from the HTML contract | agent judgement lives here, where a human reviews a PR anyway                                                                          |

The variance the control measured — three of nineteen cases flipping outcome because one analyst
decided differently from another — **cannot occur in a script-generated artifact.** Moving the
deliverable to a point before agent judgement enters is the single largest determinism win
available, and it is free in the sense that the work was going to be done anyway.

## What can be a script, and what genuinely cannot

Worth being exact, because "minimise the agent" is only useful if the line is drawn somewhere
defensible.

**Script, no agent, no ambiguity:**

- **mode decision** — call, write, grep for `sl-*` in external dependencies, classify. Probed; the
  discriminator is mechanical
- **traversal** — the capture protocol's depth rules are already an algorithm: metadata at the
  root, `get_design_context` on each child frame or instance over ~100px, recurse where the
  response has no `data-node-id` below its root, **stop at a `CodeConnectSnippet` reference**
- **classification of unresolved nodes** — suggestions call, drop descendants of resolved
  instances, drop assets, sort into the five causes. Needs the resolved set and parentage; both
  are on disk
- **every check** — reconstruction, text coverage, cross-source agreement, token existence, type
  check, render verdict. Three already exist
- **all three HTML files**

**Agent, because it is judgement:**

- what becomes a component, and what it is called
- inferring an SLDS component for an unmapped Figma one — the `inferred` basis, by definition a
  guess
- the twenty to thirty open questions per screen
- writing the framework implementation

So the agent's job shrinks to: _given a captured, verified, classified structure, decide what is a
component and write it._ Everything before that is deterministic, and **everything before that is
where the measured variance was.**

## The overlay, specifically

Per element, anchored on `data-figma-node`:

- a state — matched, approximated, inferred, invented, missing
- on hover or click: what the design said, what was emitted, the delta, the basis, and the cause
  if unresolved
- colour by state, so the shape of the problem is visible before anything is read

This is the thing that makes "no decisions handed to humans" work. A human is not asked to resolve
an element; they **look at a page and see where the run was unsure**. Aggregated across a corpus
it becomes the per-pattern question — _these nine tokens never reach their designs, which do you
want?_ — rather than a per-element queue.

It also needs nothing new: the state comes from `decisions.jsonl`, the anchor from
`data-figma-node`, and the geometry is already in the design HTML.

## The open question this does not settle, and the cheapest way to settle it

**Can a script produce 2.1 faithfully?** `render-design.mjs` exists and converts captures to HTML,
but its own header is explicit: _"a completeness probe, not a fidelity target… it will never match
the reference pixel for pixel — text layout, font metrics and effects are not reproducible this
way — so it must never be scored against the PNG."_

That is a statement about the current converter, not a proof about the data. `get_design_context`
returns resolved values inline, which is the hard part. Whether what it returns is **enough for
visual fidelity** has never been tested, because the probe was never meant to be.

**The experiment is cheap and comes before everything else in the plan.** Take one well-captured
run, render it, compare to the reference, and measure how far off it is and in what. If the gap is
small the HTML-first position is sound. If the gap is large and structural, 2.1 needs more than
the captures hold, and that changes what Phase 1 must collect — which is much better learned now
than after the registry is keyed.

Call it **T0**: cheaper than T1, and it tests the premise everything else rests on.

## What this does to "our metadata"

The instinct was right and the artifact is thinner than it sounded. There is **no transformation
of Figma's output into a common format** — transforming raw output loses fidelity and adds a place
to be wrong, and `get_design_context` already emits structured JSX with `data-node-id` on every
element.

What is ours, and what carries a validated schema:

- **capture index** — what was fetched, by which call, truncated or not (exists)
- **run record** — what was decided, append-only
- **decision record** — per element: source, emitted, basis, delta

The captures stay raw. The schema sits on the records that describe them, not on the bytes.

# Three robustness questions

## 1. What is the contract with Figma, and what happens when it moves

**There is no official library for consuming what we consume.** The repository has three official
Figma packages — `@figma/code-connect` 2.0.1, `@figma/plugin-typings`,
`@figma/eslint-plugin-figma-plugins` — and all three are for **authoring**: writing mappings and
writing plugins. Nothing official describes or types the MCP server's responses.

And those responses are not a versioned contract. Everything we know about their shape was found
by being surprised:

| Behaviour                                                                                                                       | How we found out                                    |
| ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `get_screenshot` has four modes — exact, canvas bleed, downscale to a 1600/1280 long edge, **and halving every colour channel** | measuring captures                                  |
| `get_metadata` returns XML                                                                                                      | the repository's formatter rejecting a `.json` file |
| `get_design_context` returns the code **plus five advisory blocks**                                                             | a renderer feeding prose to a TSX parser            |
| `get_code_connect_map` appends an English sentence to `{}` on timeout                                                           | invalid JSON in a `.json` file                      |
| nested instance ids are rejected by a format check                                                                              | a run concluding the interior was unmapped          |
| `hasTemplate: false` is a third state between resolved and absent                                                               | a run nearly halting on it                          |

Six undocumented behaviours, four of which cost a run. **This is the least defended dependency in
the design.**

**So yes, validate — but at the boundary, not at the end.** Validating the final artifact means
every decision was already made on data nobody checked; the failure surfaces far from its cause.
Validate each response **as it is captured**, which is where the shape is known and where a
failure is still actionable: retry, record, or stop.

Two constraints on how:

- **It must not transform.** The capture protocol's rule — a capture file holds exactly what the
  call returned — is what lets a reader be rewritten later when it turns out to be wrong. So:
  capture raw, validate a _parsed view_ of it, and record the verdict in `index.json` beside the
  bytes. The bytes never change.
- **The point is not correctness, it is noise.** A schema over an undocumented format will break
  when Figma changes something. That is the feature. It converts a silent shape change — which in
  this project has meant a confident wrong number every single time — into a loud failure at the
  one place that knows what was expected.

`zod` is not in the repository today; it would be a new, small dependency.

**One question this raises and does not settle:** the Figma **REST API is documented and
versioned**, where the MCP server is neither. The MCP server is what gives us Code Connect
resolution and design context. It may be right to take structure from REST and semantics from
MCP, rather than everything from the undocumented surface. Worth deciding deliberately.

## 2. Where the agent sits, and what it reads

**The agent interprets from disk, never during the fetch.** Four reasons, each from something
that happened:

- a crash mid-interpretation costs nothing, because the call was already persisted;
- the same bytes can be re-read when a reader turns out to be wrong, which happened twice;
- the interpretation becomes reproducible — re-run it on the same bytes and compare;
- the payload stays out of the context window. One call returned 2.18 MB; an agent that reads
  responses as they arrive loses its context to that.

**The agent should almost never open a raw capture.** It reads the small derived files — the
index, the classification, the decision record — and greps a capture when it needs one specific
thing. That rule is what keeps the 2.18 MB incident from recurring by accident.

So the shape is: **a skill the agent invokes runs the scripts; the scripts write; the agent reads
what the scripts derived.** Three points where it acts, and nowhere else:

1. **after capture and validation** — decide component boundaries and names, reading the index,
   the classified unresolved list and the reconstruction;
2. **implementation** — write the code for one component, reading its spec and the relevant
   capture excerpt;
3. **review** — read its own output.

Mode, traversal, classification, every check and all three HTML files involve no agent at all.

## 3. Can we know we have everything? Not as a proof, and that is the right answer

**We cannot prove 100%, and aiming at a proof would be aiming at the wrong thing.** Where Code
Connect resolves, we _deliberately_ do not hold the interior — the snippet is the authority and
going deeper returns nothing. So "100% of the screen" and "100% of what is needed to reproduce
it" are different quantities, and they differ exactly at the mapped nodes.

The honest formulation is **completeness per region against a stated boundary**:

| Region               | Complete when                                      |
| -------------------- | -------------------------------------------------- |
| mapped               | the mapping is recorded — by virtue of the mapping |
| unmapped             | its own `get_design_context` is captured           |
| hidden or decorative | it is explicitly excluded, with the reason         |

A region in none of the three is a gap. That is `T-NOJIRA-figma-to-code-06`, node accounting, and
it is the only true completeness check we have — the others sample.

It is also **half built already**: the capture protocol counts node ids, and that count is how we
know 3,004 were stored and a reader could read 2,114. Closing the loop means comparing the ids we
hold against the ids the metadata tree declares, and assigning every one to a bucket.

**And the limit that remains, stated rather than hidden:** `get_metadata` itself stops at instance
boundaries — A2's 10,936-node design returned 27. So the tree we account against is the
**placement-level view**, not every node in the file. That is the right view to account against,
because it is the view a developer works in. But our completeness is _relative to it_, and anyone
reading a completeness figure should know which tree it counted.

Three tests, in increasing rigour and cost: the **reconstruction** says the regions are there
(exists, eleven of nineteen runs failed it); **text coverage** says nothing visible went
unrecorded (the check that would have caught the consent sentences); **node accounting** proves
every declared node has a home. The first two are cheap and catch what actually went wrong.

# A common format, after all — I argued against this and was wrong

I said: do not transform Figma's output, the captures **are** the representation, transforming
loses fidelity and adds a place to be wrong.

That objection is true and shallow, and the counter-argument is stronger. **Without a common
format, every consumer re-parses an undocumented format, so each embeds its own assumptions about
it.** Two things already in this repository are that failure:

- the capture protocol records that **3,004 node ids were stored and a reader built for the job
  could read 2,114** — the reader's assumptions did not match the data, and nothing said so;
- the advisory-block problem, where the renderer selected on `call === "get_design_context"` and
  **"a correct `call` and a separate entry were mutually exclusive"** — a parsing assumption
  leaking into the storage schema.

And the point that settles it: **without a common format the generator cannot be tested without
calling Figma.** Its tests would depend on a live, undocumented, rate-limited surface. For the one
artifact whose whole value is determinism, that is untenable. With a format, the generator is
tested against fixtures and never calls anything.

## It does not conflict with keeping captures raw — those are different layers

| Layer             | What it is                             | Changes when           | Validated by                  |
| ----------------- | -------------------------------------- | ---------------------- | ----------------------------- |
| **raw captures**  | exactly what Figma returned, immutable | never                  | nothing — it is evidence      |
| **adapter**       | Figma's shapes → ours                  | Figma changes          | its output against the schema |
| **common format** | our vocabulary, one version            | we decide to change it | `zod`, at the boundary        |
| **generators**    | HTML, overlay, progress, checks        | our logic changes      | unit tests on fixtures        |

My rule should have been "**no transformation of the stored evidence**", which is compatible with
an adapter and is what the protocol actually protects. The raw bytes stay so the adapter can be
rewritten when it turns out wrong — which, on an undocumented format, it will be.

## What this buys, in the terms the question was asked in

**"We will not know what broke."** With this split a failure is one of exactly two things, and
they are attributable without investigation:

- the **adapter's output fails the schema** → Figma changed something. One place, loud, with the
  raw bytes beside it to diagnose from.
- a **generator test fails** → our logic. No Figma involved.

**"It will be hard to monitor quality and progress."** Both are computed over the common format,
so neither moves when Figma changes its wire shape. A progress view reading our format keeps
working across a Figma change that breaks ingestion — and says so, which is the useful behaviour.

# Images

`download_assets` returns three things per node: `export` (a render of the whole node),
`rawImages` (the original uploaded JPEG/PNG/GIF/WebP fills in the subtree, **capped at 20**, each
with its actual `format`), and `svgAssets` (vector layers best represented as SVG — icons, logos
— **capped at 20**, the same set `get_design_context` surfaces).

Four things follow, and the first is not optional.

**Download during capture, never later.** The contract says it plainly — _"URLs are temporary —
download promptly."_ One run recorded exactly this: _"expect these URLs to 404 after expiry; do
not invent local asset files to replace them."_ Every missing-image discrepancy in the batch is
this, and a later pass cannot fix it because the URLs are gone.

**Resolve the mapping first, then download what is still an image.** An icon that maps to
`sl-icon` is a component, not an asset, and downloading it as a raster converts a mapped
component into a picture. The traversal already knows which nodes resolved — asset collection
belongs after that branch, not before.

**The caps are a traversal constraint.** Twenty raw images and twenty SVGs per call means a dense
screen needs per-node calls, which the depth rules already produce. A run that calls once at the
root and assumes it has everything will silently hold twenty of forty.

**Store like any other capture**, and let the common format reference the local file rather than
the Figma URL: `captures/assets/<nodeId>.<format>`, with the index recording node, source URL,
format, bytes and `fetchedAt`. The expiry is why `fetchedAt` matters here more than elsewhere.

# The completeness mechanism — the biggest unknown, made mechanical

Three checks over the common format, which together answer "could we rebuild this screen".

**1. Geometry coverage.** `get_metadata` gives `x/y/width/height` for every node in the placement
tree. For each, ask whether the format contains an element at that position and size within a
tolerance. Present or missing, per node, with a name.

**2. Text coverage.** Every text node's content appears somewhere in the format. This is the check
that would have caught the three consent sentences that existed in no capture and survived only
because an implementer read the screenshot.

**3. Asset coverage.** Every node with an image fill has a downloaded file in the index.

**With two exemptions, stated rather than assumed:** a **mapped** region is complete by virtue of
its mapping — Figma substitutes the reference and going deeper returns nothing — and a **hidden or
decorative** node is complete by being explicitly excluded, with its reason recorded.

The output is not a yes or no but a **coverage figure plus the list of what is missing, by node id
and name**, which is the form a human can act on and a trend can be plotted from.

**And it is falsifiable against what we already have.** Run it over the nineteen runs: if it
reports high coverage for a run whose reconstruction visibly lacks half the screen, the mechanism
is wrong. Eleven of nineteen failed the reconstruction probe, so there is a known-bad set to test
against — the mechanism has to agree with it or explain why not.

That is the strongest validation available: **the check is tested against runs whose answer we
already know.**
