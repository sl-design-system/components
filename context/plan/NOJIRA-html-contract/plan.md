# The HTML contract and the common format it is generated from

> Derived from [A-NOJIRA-pipeline-staging](../../analyzes/NOJIRA-pipeline-staging/analysis.md),
> with the sequencing argument in
> [`sequencing.md`](../../analyzes/NOJIRA-figma-to-code/sequencing.md) and the deliverable
> described in [`html-first.md`](../../analyzes/NOJIRA-figma-to-code/html-first.md).

## Goal

Produce the artifact a developer receives, and the apparatus that measures it, from data already
on disk.

Three HTML files, all generated by script from one schema-validated format: **the design**, which
renders as the Figma does; **the overlay**, which marks per-element what matched and what did
not, inspectable; and optionally **the progress view**. Framework code is generated later, from
the HTML rather than from Figma, and is out of scope here.

The measurable outcome: **the first comparable numbers across the nineteen existing runs.** There
are none today — each run measured itself, in prose, by its own method, some against a distorted
reference. Nothing in the corpus supports "this run was better than that one".

## Approach

**Build the measuring apparatus over captures already on disk, before touching Figma again.**

The nineteen runs cost roughly 8M tokens to produce and their captures are committed. The adapter
and the generators read them and need no API calls at all, which makes every step here
repeatable, free to re-run, and independent of Figma's availability or its undocumented response
shapes.

Three consequences shape the work:

**The format is designed from requirements, not from the data.** The captures were made before
the capture protocol existed, with improvised depth — eleven of nineteen fail the reconstruction
probe. The adapter must _report_ what is missing rather than the schema shrinking to fit, or the
contract inherits their gaps permanently.

**A script has no judgement, so two runs produce identical bytes.** That is the design system
team's repeatability goal satisfied by construction rather than by discipline, and it is checkable
as a checksum comparison rather than argued.

**Raw captures stay raw.** The adapter reads them and never rewrites them, so it can itself be
rewritten when it turns out wrong — which, over an undocumented format, it will be.

## Scope

**In:** the common format and its `zod` schema; the adapter from captures; the three generators;
the closure check that says whether a capture was complete; retrofitting all nineteen runs.

**Out:** framework code generation; any change to how Figma is called — that is
`P-NOJIRA-figma-ingestion`; the discrepancy registry, which
[A-NOJIRA-figma-metadata-contract](../../analyzes/NOJIRA-figma-metadata-contract/analysis.md)
blocks on `data-figma-node` existing first.

## Work breakdown

- `T-NOJIRA-html-contract-01` — The common format: schema derived from the contract analysis's
  requirements, expressed in `zod`, with a validating reader
- `T-NOJIRA-html-contract-02` — Adapter from captures to the format, reporting gaps rather than
  hiding them
- `T-NOJIRA-html-contract-03` — Retrofit: run the adapter over all nineteen runs; the runs it
  cannot adapt are the incomplete captures, named
- `T-NOJIRA-html-contract-04` — The closure check: every visited node resolved, captured,
  descended, hidden or excluded, and the frontier empty
- `T-NOJIRA-html-contract-05` — Generator 1, the design HTML, from the format alone
- `T-NOJIRA-html-contract-06` — Determinism proof: generate twice, compare checksums, across all
  adaptable runs
- `T-NOJIRA-html-contract-07a` — Reference integrity: verify each run's reference image against
  the frame's declared size and detect the halved-colour-channel case; refuse a distorted
  reference rather than correcting it
- `T-NOJIRA-html-contract-07b` — Fidelity of the generated design against a verified reference,
  measured and reported per run — the first comparable number
- `T-NOJIRA-html-contract-08` — Generator 2, the overlay, with per-element state and inspection
- `T-NOJIRA-html-contract-09` — Generator 3, the progress view
- `T-NOJIRA-html-contract-10` — Fixture-based tests for every generator, so none of them needs
  Figma to be tested

**The numbers are the execution order.** 01 to 04 answer whether the idea is coherent and cost
nothing; 05 to 07 produce the first comparable measurement; 08 and 09 are the viewers; 10 is what
keeps the generators testable as they change.

Three orderings are load-bearing. **04 before 05**, because generating HTML from an incomplete
capture produces a plausible wrong picture, which is this project's signature failure. **06
before 07b**, because a fidelity number from a non-deterministic generator cannot be compared
with anything, including itself. And **07a before 07b** — caught in review and nearly missed:
`get_screenshot` has four behaviours including **halving every colour channel**, so a fidelity
number computed against an unverified reference is a number about a corrupted ground truth. The
context states the rule plainly — verify and refuse, never reconstruct — and this plan would have
violated it at its most important task.

## Risks & dependencies

**The schema gets fitted to the captures we happen to hold.** The most likely failure, because it
is the path of least resistance when the adapter fails. Mitigation: 01 lands before 02, derived
from the requirements the contract analysis enumerated, and 03's output is a list of gaps rather
than a reason to weaken 01.

**The design HTML cannot be made faithful from the captures.** `render-design.mjs` exists and
disowns fidelity in its own header — but that is a statement about the converter, not about the
data. 05 settles it. If the gap is large and structural, it changes what Phase 1 must capture,
which is much cheaper to learn here than after the registry is keyed.

**The overlay has no decisions to show on historical runs.** The nineteen hold open questions in
prose, not structured decisions, so 08 over them will be partial. That is a finding about what
the run record must carry, not a blocker — and it is why 08 sits after the measurement tasks
rather than before.

**It depends on the captures being readable at all.** 3,004 node ids were stored and a reader
could read 2,114. If 03 cannot adapt most runs, this plan's premise — that value can be extracted
from data already paid for — is wrong, and the work moves to `P-NOJIRA-figma-ingestion` first.

**Dependency, one way — with one correction from review.** Nothing here needs
`P-NOJIRA-figma-ingestion`; that plan needs this one, having nothing to measure against until
07b exists. The correction: reference integrity is an ingestion concern, and this plan needs it
first, so 07a lives here rather than there. Verification is cheap and local; fixing the capture
is not, and belongs to the other plan.

## Acceptance

- The format has a `zod` schema derived from stated requirements, and a reader that rejects what
  does not match.
- The adapter runs over all nineteen runs and, for each, either produces a valid format document
  or names what is missing. Neither outcome is silent.
- The closure check reports a census — visited, resolved, captured, descended, hidden, excluded,
  frontier — and agrees with the reconstruction probe's verdict on the eleven runs known to fail
  it, or explains why not.
- The design HTML generates from the format with no Figma call, and **generating twice produces
  identical checksums** for every adaptable run.
- Each run's reference is verified before any number is computed against it, and a distorted
  reference is refused rather than corrected.
- Every run that generates has a fidelity figure against a **verified** reference, produced by
  the same generator and therefore comparable across runs.
- Every generator has tests that run on fixtures, with no network access.

## Approval

Not approved. Two open questions in the frontmatter need answers before `sl-tasks`, and one of
them — whether the HTML is the deliverable or only the probe — changes the plan's purpose rather
than its detail.
