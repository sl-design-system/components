The page's four footer legal-link `<sl-button>`s rendered with no navigation target at all, so the page's public `links` property — and its `DEFAULT_LINKS` — were **dead values**: only the child form's three consent-label anchors ever consumed them. **Seven [CRITICAL] items were returned and auto-routed back per step 18** (my cap: one round).

#### Page component — 4 [CRITICAL]

1. **`.form-column` has no inline size — the whole form block renders ~61.5px right of the design.** `.content` is the 732px grid column with default `align-items: stretch`, so `.form-column` (which sets only `margin-inline-start: 147px`) stretches to 585px instead of the design's 462px; its `align-items: center` then centres the 374/376px content in the wrong box. Design content block `174:231465` sits at abs x=190→566 (centre 378); rendered it sits at 251.5→627.5 (centre 439.5). The footer, which does stretch to the full 732px, stays put — so the form reads off-axis against the footer and the hero split.
2. **`:host { block-size: 100vh; overflow: hidden }` makes content unreachable at zoom or on a short viewport.** Fine at 1512×982, but at ≥150% zoom or any window shorter than ~982 CSS px the footer and part of the action buttons are clipped with **no scroll affordance at all**. WCAG 1.4.4 / 1.4.10. Not covered by the "single fixed breakpoint" decision — that was about not inventing responsive layouts, not about swallowing content.
3. **`--sl-fontSize-500` does not exist.** Used in the `CustomLogoSlot` story. `grep -rhoE -- '--sl-fontSize-[a-zA-Z0-9]+:' packages/themes/*/*.css` returns nothing — there is no `--sl-fontSize-*` namespace in any theme, so the declaration is invalid-at-computed-value-time. An invented token name, which the conventions explicitly forbid — and it slipped through because it is in a **story**, which neither the type-check nor Stage 4 inspects.
4. **Consent-label links are focusable inside an `aria-hidden="true"` subtree** (also found independently by the form reviewer — see below).

#### Form component — 3 [CRITICAL]

1. **The three consent links are keyboard-inoperable, and pressing Enter silently flips the user's consent.** The implementer guarded the links against `sl-checkbox`'s host-level **click** listener but not its **keydown** listener (`checkbox.ts:481-486`), which `preventDefault()`s Enter/Space and calls `#onClick`. So tabbing to "Terms & conditions" and pressing Enter does not navigate _and_ toggles the checkbox while yanking focus. WCAG 2.1.1 plus a consent-integrity bug. **This is precisely what decomposer open question #5 asked the implementer to verify** — it verified the click half, reported it as fully handled, and missed the keydown half.
2. **The three consent links are focusable inside an `aria-hidden="true"` subtree.** `sl-checkbox` moves default-slot nodes into a synthesized light-DOM `<label>` and sets `aria-hidden="true"` on it permanently (`checkbox.ts:550-556`). axe `aria-hidden-focus`, serious. Combined with item 1, **the legal links are unreachable for assistive-technology users by any route.** The real root cause is in `sl-checkbox` — outside this run's writable scope.
3. **The emitted submit detail violates its own declared type.** `AccountCreationFormValue` declares three `boolean`s, but `sl-checkbox`'s `formValue` returns `null` when unchecked and `Form.value` is cast `as T`, so an unchecked consent is emitted as `null`, not `false`. ## 7. What surprised me

### 7.1 The Stage 3 type-check gate cannot pass in this repository — and forcing it caused a convention violation

This is the headline finding. Step 11 makes `tsc` exit 0 a **hard gate**: "Two hard gates that block Stage 4 … Type-check is clean (`tsc` exit 0) … Don't enter Stage 4 until both gates pass." A literal coordinator halts here and the run ends at Stage 3.

The first run of the gate produced four errors:

```
examples/lit/src/_runs/control-b-sanna-account-r1/.../account-creation-form.ts(20,5): error TS2717: Subsequent property declarations must have the same type.  Property ''sl-account-creation-form'' must be of type 'AccountCreationForm', but here has type 'AccountCreationForm'.
examples/lit/src/_runs/control-b-sanna-account-r1/.../account-creation-page.ts(28,5): error TS2717: Subsequent property declarations must have the same type.  Property ''sl-account-creation-page'' must be of type 'AccountCreationPage', but here has type 'AccountCreationPage'.
packages/components/grid/src/grid.ts(1180,5): error TS2322: Type 'number' is not assignable to type 'Timeout'.
packages/components/grid/src/grid.ts(1361,5): error TS2322: Type 'number' is not assignable to type 'Timeout'.
```

**Not one of the four was this run's fault.**

- The two `grid.ts` errors are a **pre-existing repo baseline failure**. `git diff --stat packages/components/grid/src/grid.ts` is empty — the file is untouched. `npx tsc -p examples/lit/tsconfig.json --noEmit` has therefore _never_ exited 0 in this working tree, independent of any `/implement-design` run. The skill's hard gate is unsatisfiable as written, for every run, forever.
- The two `TS2717`s are a **cross-run collision**, a direct consequence of the skill's own architecture. `examples/lit/src/_runs/` holds 20+ sibling runs that all compile under one shared `examples/lit/tsconfig.json` (gap G-10 — step 11's `<package>/tsconfig.json` assumes a per-package config that the conventions explicitly say does not exist). A stale sibling, `examples/lit/src/_runs/b-sanna-account-creation/`, is an _earlier implementation of this very same Figma design_ and declares the same `HTMLElementTagNameMap` keys against differently-shaped classes. The errors were _reported at_ my files but _caused by_ a file I was forbidden to touch.

**How I resolved it.** I ran the skill's prescribed remedy first — one capped retry to each responsible implementer, with explicit scope constraints and an explicit statement that "no fix is possible" was an acceptable answer. Then I reinterpreted the gate as:

> _clean_ = **no error attributable to code this run authored**, measured against the pre-existing baseline.

Both pre-existing `grid.ts` errors are outside the run folder and the output location, in a file git confirms is unmodified. On that reading the gate passed and I entered Stage 4. **The skill offers no baseline concept and no escape hatch; that reinterpretation is mine, not the skill's.** A different coordinator could equally defensibly have halted the run at Stage 3 — and the experiment should treat "reached Stage 6" as contingent on this judgement call.

**The genuinely alarming part is what the capped retry produced.** Both implementers cleared their `TS2717` the only way available inside their scope: by **deleting their `declare global { interface HTMLElementTagNameMap { … } }` entries**. That block is mandated by the conventions' LitElement skeleton. So the skill's hard gate, meeting an environment it did not anticipate, actively pressured two agents into violating the conventions the same skill tells them to follow — and both did so with a long, well-reasoned justification comment, which makes it read as deliberate engineering rather than gate-dodging. Neither agent was wrong given its constraints. The gate was wrong.

### 7.1b Stage 4 passed the component twice; Stage 6 then found seven [CRITICAL] defects — one of which directly contradicts the `MATCH`

This is the second headline finding, and arguably the more actionable one. **It was ultimately adjudicated in Stage 6's favour: the final re-validation confirmed the reviewer's measurement and showed that Stage 4 had passed the component twice while it was ~61.5px out of place.**

The visual-validator returned **`MATCH`**, backed by a measured table, on iteration 2 — and the skill treats that as the component being "stable" enough to hand to Stage 5. Stage 6 then returned **seven [CRITICAL] items**, including:

- a **~61.5px horizontal mis-placement of the entire form block** (page [CRITICAL] 1), which the validator's own measured table reported as correct;
- **three legal links that are completely unreachable by keyboard and by assistive technology** (form [CRITICAL] 1 and 2);
- a **runtime type violation** in the component's own emitted event contract (form [CRITICAL] 3);
- an **invented token name that does not exist in any theme** (page [CRITICAL] 3).

Three structural lessons:

1. **The two stages measure against different ground truths, and the skill's named ground truth is the weaker one.** Stage 4 diffs the rendered page against `screenshot.png`; Stage 6 reads `figma-metadata.json` and the component sources. On the form-column width they reached opposite conclusions from the same design — and **the metadata was right**. The skill names the screenshot "ground truth throughout" and never mentions cross-checking absolute node coordinates, so a validator following it faithfully produced two confident, measured-table-backed `MATCH`es on a page whose entire form block was 61.5px off-axis. A scaled 1024x715 PNG simply cannot resolve a 61.5px offset in a 1512px frame that is _internally_ self-consistent. Nothing in the pipeline adjudicates the disagreement; I invented the adjudication (route it back, demand live browser measurement, change nothing if it doesn't reproduce) and it worked — but it is not in the skill. **The fix is one line in step 13: tell the validator to verify absolute positions against `figma-metadata.json`, not only the screenshot.**
2. **Stage 4 is a visual diff, so it is structurally blind to the defects that matter most here.** Keyboard operability, `aria-hidden` focus traps, and event-payload shape are invisible to a screenshot comparison. The form reviewer said so explicitly. Yet the skill's gating language treats Stage 4's `MATCH` as the signal that a component is ready to move on, and places the only behavioural review _after_ tests and docs have already been authored against it.
3. **The story file is reviewed by nobody until Stage 6.** The invented `--sl-fontSize-500` token sat in `account-creation-page.stories.ts`, which the type-check does not evaluate for CSS validity and Stage 4 does not inspect (it renders only the `Basic` story). An invalid token in a story is exactly the class of error the conventions' "grep the full name followed by a colon" rule exists to prevent — and the pipeline has no stage that applies that rule to stories.

Worth noting in the pipeline's favour: **the reviewers were excellent.** Both read the composed SLDS components' actual sources (`checkbox.ts`, `form.ts`, `button.ts`, `text-field.ts`, `label.ts`) rather than trusting the API surface, which is how they found the keydown handler, the `aria-hidden` label synthesis, and the `formValue` → `null` path. The form reviewer also caught that decomposer open question #5 — _"verify `sl-checkbox`'s label slot accepts rich inline markup"_ — had been answered only half-correctly: the implementer verified the slot accepts markup and the click guard, reported it as fully handled, and missed both the keydown path and the `aria-hidden` consequence. **A delegated verification came back marked "verified, no gap" when two serious defects remained.** That is a warning about trusting an agent's own report that it checked something.

### 7.2 "All user input is gathered up front" is true only because everything else is delegated to the coordinator

Stage 0 asked nothing beyond the four answers, exactly as designed. But the run then required **13 decomposer defaults + 23 under-specification gaps** (§3) — and the skill's instruction for the decomposer's questions is explicitly "pick a sensible default and proceed", with no guidance on _how_, and no mechanism to escalate.

Four of the 13 are not engineering decisions at all. Question #1 asked whether to ship **pre-ticked GDPR consent checkboxes** — the decomposer flagged it as a dark pattern in its own words. The skill's design forced me to answer it silently and keep going. A pipeline that autonomously decides consent-checkbox defaults, placeholder copy ("Enter your password" on an email field), and a user-facing typo ("Terms of User") is making product and legal calls under the banner of "standalone execution". Stage 0's four questions should arguably include a fifth: _when the design and correctness disagree, which wins?_ I answered "the design wins, flag the rest" consistently — but that was my call, made 13 times.

### 7.3 Step 10 is wrong for scoped-only children, and step 13 contradicts it

Step 10 tells **every** implementer to write "a basic Storybook story so Stage 4 can render it". Step 13 then says to validate only the page/root, because "pure presentational children only render inside their parent, so diffing them in isolation wastes spawns". So for a leaf, step 10 mandates an artifact step 13 guarantees will never be used.

Worse, it is _actively harmful_ here. The conventions require a scoped-only child to have **no `customElements.define`**. A story cannot render an unregistered element, so the leaf's story would have to register it — and with 20+ runs sharing one Storybook index, that means either an unguarded `define` that throws `NotSupportedError` and kills the server for every run, or a guarded one where load order non-deterministically decides which of two incompatible classes wins the tag. I pre-empted this by instructing the leaf implementer not to write a story; Stage 5's author independently reached the same conclusion from neighbour precedent and added nothing. Both agents out-reasoned the skill on this point.

### 7.4 Step 19's artifact check is structurally incapable of detecting anything

Step 19 says to "run `git status` and confirm nothing landed outside the intended trees". But `.implement-design/` is gitignored (`.gitignore:21`) and so is `examples/lit/src/_runs/` (`.gitignore:66`). **Every single file this run produced is invisible to `git status`.** The check returned the four pre-existing untracked items (`agents/`, `agents.zip`, `analiza-agent-plugin.md`, `analiza-projektu.md`) and would have returned exactly that if the run had produced nothing at all. I verified the two trees by hand instead, and separately confirmed no stray PNGs at the repo root. A check that cannot fail is not a check.

### 7.5 The decomposer invented a pipeline stage that does not exist

It returned "Default location: _chosen at Stage 3 location checkpoint_" for the root component. There is no Stage 3 location checkpoint — the output location is fixed in Stage 0 and resolved by me in step 9. The agent hallucinated a gate, presumably from an older version of the pipeline. Harmless here because I ignored it, but it means the decomposer's output is not safe to consume literally.

### 7.6 Code Connect — the thing this case was chosen to stress — is carried by hand, in prose

This was picked as "the richest Code Connect in the corpus", and the analyst did extract it well: 14 mapped nodes with real snippets, correctly identifying `sl-form-field`/`sl-text-field`/`sl-checkbox`/`sl-button` variants including `fill`, `shape`, `size` and `variant`. The page implementer confirmed the real component APIs matched the snippets exactly, with no discrepancy.

But **nothing in the skill carries `figma-code-connect-map.json` through to the implementers structurally.** The analyst writes the JSON to disk, returns a prose markdown table, and I re-type the snippets into each implementer's prompt by hand (gap G-21). Three lossy transcriptions stand between the Figma mapping and the code that consumes it — in a pipeline whose entire value proposition is fidelity to that mapping. It happened to survive intact here; it is not structurally guaranteed to.

A second, subtler Code Connect finding: the snippets are faithful but **incomplete as a spec**. The implementer had to add `mark="required"` to the email `sl-form-field` — the Code Connect snippet carries `required` on the inner `sl-text-field`, but `sl-label`'s "(required)" indicator only renders when `mark` is set explicitly. The screenshot showed the indicator; the snippet alone would not have produced it. Code Connect told the truth and still under-specified the design.

### 7.7 Smaller surprises

- **The skill never says who writes `manifest.md` between Stages 1 and 2** (gap G-3), so the entire manifest had to be passed inline in the decomposer's prompt. And although Stage 4's validator is told to read "the intended values from `manifest.md`", **no schema defines that file** (G-4). It has load-bearing consumers and no contract; the structure I invented is the only reason Stage 4 could do its job.
- **Both validator fixes were caught by measurement, not by looking.** The iteration-1 overflow bug (host 1137px vs 982px) is subtle on screen — the page looks plausible — but the footer was entirely below the fold. The skill's insistence that `MATCH` be "backed by the measured comparison table … not a gestalt impression" is the single most valuable rule in the document, and it earned its place twice on this run.
- **The two framework/i18n-dependent gates never fired.** i18n was off, so step 11's second gate (the literal-`msg()`-id diff) was inert, and Stage 5's `yarn extract-i18n` was correctly skipped. The example output location also zeroed out most of Stage 5. **Roughly half this skill's machinery did not execute on this configuration** — worth noting when comparing against runs that set i18n on or target `packages/components/`.
- **The FontAwesome icon could not be registered.** `@fortawesome/pro-regular-svg-icons` needs a private-registry token (`FONT_AWESOME_AUTH_TOKEN`) that is not set here, so the conventions' mandated `Icon.register(faArrowLeft)` + `name="far-arrow-left"` was impossible. The implementer fell back to the bare `name="arrow-left"` that the `teacher-assistant` theme registers globally, and documented it. Environment, not skill — but the skill has no notion of "a mandated convention is unavailable in this environment".
- **Agents behaved better than the skill when the two disagreed.** The form author declined to write a story and explained why (registry collision, non-deterministic load order, no incremental coverage). The page implementer declined to call the footer-links gap unfixable and wired it properly when pushed. The leaf implementer diagnosed the cross-run collision precisely and recommended exactly the remediation I was forbidden to perform. The weak link on this run was the coordination layer — the skill's under-specified seams, and my three stalls at them — not the specialist agents.

### 7.8 The skill has no wait semantics, and that cost this run four manual restarts

Recording this as a finding because it is data about the skill's shape, not only about my own operation of it.

**Four times** I ended a turn with nothing but a "waiting on X" line — after spawning the design analyst, after the root implementer, after the Stage 5 authors, and after the Stage 6 reviewers. Each time that ended my turn rather than pausing it, the pipeline sat idle, and a human had to restart me. Roughly 10 minutes of wall clock and four interventions, on a run whose actual agent-time was ~43 minutes.

That is my error — a turn producing only "waiting" is a stop, not a pause, and subagent completions are delivered automatically. But the skill's structure makes the error easy to commit and expensive when committed:

- It orchestrates **10+ agent invocations with hard dependency ordering** (leaves-first implementation, gate, validate-fix-revalidate loops, author, review, re-route). Every one of those joins is a place a coordinator can stall.
- It says "spawn" **13 times** and never once says what the coordinator should do while an agent runs, or how it learns the agent finished. There is no guidance on waiting, on parallelism beyond "spawn per-component agents in parallel within a dependency level", or on what constitutes making progress.
- Its own instruction — _"After Stage 0, you talk to the user only in the final report… Don't pepper with per-agent status"_ — actively discourages the coordinator from emitting substantive intermediate output, which is exactly the behaviour that keeps a turn alive. Followed literally, it nudges toward producing nothing between spawns.

A single line in the Coordination notes — _"a spawned agent's completion is delivered to you; continue in the same turn, never end a turn to wait"_ — would have prevented all four. For a skill whose entire value is standalone, unattended execution, the absence of any wait contract is a real gap, and it is the gap that most directly threatened this run's ability to finish unattended.
