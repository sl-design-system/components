## Known Unresolved Issues in v2 (Current)

These are confirmed problems in the current `sl-ds-*` system. Any team adopting v2 should be aware of them before using it in production.

| # | Problem | Impact | Root cause |
|---|---|---|---|
| **1** | **No pixel-perfect output** | Generated screens visually differ from Figma — wrong colors (Sanoma teal vs SLDS blue), missing styles, wrong layouts | Theme override file not generated (R6). Skills use `--sl-*` var names correctly but SLDS generic theme resolves them to wrong values for this project. |
| **2** | **RWD not working** | Generated components use fixed pixel widths from Figma, do not scale on mobile/tablet | No responsive breakpoints generated. PLAN.md captures Figma absolute positions but skills have no step to convert them to fluid/responsive CSS. |
| **3** | **Plan requires low-level manual review (design intent: architecture-only)** | PLAN.md goal: developer reviews ONLY high-level architecture (component split, feature structure). Plan review must be architecture-only; all low-level correctness should be automated. |
| **4** | **Router not tested in practice** | `/sl-ds` router state machine behavior on real workflows is untested | The router skill was built but no end-to-end test of the full state machine (`virgin → configured → in-progress → completed → stale`) has been run. |
| **5** | **Architecture and layout skills untested** | `/sl-ds-setup`, `/sl-ds-layout` exist as skills but have never been run against a real project | These were defined as part of the 15-skill ecosystem but Desktop-6/7 test runs skipped directly to `/sl-ds-plan`. |
| **6** | **Standards context overflow** | `.agents-v2/standards/fe/` files are too large — loading them fills the LLM context window, leaving no room for actual generation | No solution implemented. | **7** | **Shallow resumability (phase-boundary only)** | Resume protocols ARE written per skill but only work at phase boundaries. | **8** | **No accessibility in generated code** | All generated components lack ARIA labels, keyboard navigation, focus management. WCAG non-compliant by default. | No a11y skill in v2. ## What This Is

A set of AI agents/skills (Markdown instruction files for Claude Code) that automate the **Figma → Angular/SLDS code generation** pipeline for the Sanoma Learning Design System.

**v1 (`ds-*` + `sdl-*`):** Two-layer system. The `ds-*` layer (10 agents) handles Figma interpretation, SLDS component mapping, and architecture planning. The `sdl-*` layer (30+ workers) handles code generation, quality verification (real shell commands), gap analysis, testing, and CI/CD. A developer calls `ds-impl` which drives the `ds-*` pipeline, then either does direct integration or hands off to `sdl-master` for full sprint execution.

**v2 (`sl-ds-*`):** Single-layer system of 15 skills driven by a router. Uses newer Figma MCP tools (`get_design_context`, `get_code_connect_map`, `get_variable_defs`) that didn't exist when v1 was designed. Makes PLAN.md a mandatory, human-reviewable checkpoint before any code is generated.

### R1 — Pixel-perfect output from Figma

**Problem it solves:** Manual CSS tweaking after AI generation was taking as long as coding from scratch. Developers were spending more time fixing generated output than the generation saved.

**What it means:** Generated Angular code must visually match the Figma design exactly — correct layout, colors, typography, spacing, component types — without post-generation manual fixes.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — Visual Fidelity gate is structural/token-based: "correct DS components + correct props + correct tokens + correct layout = visually correct by definition." Screenshot comparison explicitly rejected as primary gate. Quality metric VF1–VF9 run via static analysis. Never validated against real rendering. | ⚠️ **Partial** — Pixelmatch against live rendered output + composite Design Fidelity Score. Real rendering comparison. Depends on R6 (theme) being resolved — currently generates SLDS generic colors (blue) when Figma shows project-specific colors (teal). |

### R2 — Application architecture: selection, proposal, enforcement

**Problem it solves:** AI generated components in random locations and structures. No consistency across screens. "Per-feature" vs "per-type" vs "per-layer" decisions were made ad-hoc.

**What it means:** Skills must (1) propose an architecture pattern at project start (e.g. per-feature under `features/`), (2) detect if architecture already exists, (3) enforce that every new component lands in the right place consistently, (4) ask the developer to confirm/adjust the pattern via structured questions.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-compose` classifies each component as SMART/DUMB, assigns NX layer (feature/ui/data-access), checks workspace with `check-architecture.js`. Smart/dumb split is quantitative (>150 LOC, >30 bindings, stateful interaction). But the architecture PATTERN (per-feature vs per-type) is not explicitly proposed or confirmed with the developer. | ⚠️ **Partial** — `sl-ds-plan` produces architecture section in PLAN.md (structure: per-feature / per-type / hybrid) and asks developer to approve via AskUserQuestion. PLAN.md frontmatter carries the chosen pattern. But no cross-screen enforcement mechanism — each plan can choose differently. |

### R3 — App layout pattern: create, maintain, reference to Figma

**Problem it solves:** Each screen was generated with its own ad-hoc shell/layout. The app-level structure (topbar, primary layout, secondary layout, slots) was inconsistent and not tied to the Figma layout specification.

**What it means:** Skills must create a reusable APP LAYOUT PATTERN early (shell component, primary layout, secondary layout slots). This pattern is stored as a design decision, referenced by all subsequent screens, updated when Figma's layout changes, and enforced consistently across all implementations. This is not about detecting component clusters — it is about the application's structural skeleton.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-figma` Pass 3 extracts layout semantics (direction, gap, padding, alignment, responsive). `ds-compose` Step 4 assigns route/shell placement. But no explicit "create layout pattern document" step and no mechanism to enforce it across future screens. | ⚠️ **Partial** — `sl-ds-layout` is a dedicated skill for layout analysis before planning. It produces a layout design decision document. But the update/enforcement across subsequent runs is not formally specified. |

### R4 — Project setup verification before generation

**Problem it solves:** Skills were attempting to generate components without first checking whether the project had been set up (architecture pattern chosen, layout pattern created, DS installed). This caused inconsistent output and wasted generation runs.

**What it means:** Before generating any screen-level code, skills must verify: (1) is the DS installed? (2) has the architecture pattern been decided and documented? (3) has the app layout been created? If any of these is missing, redirect to the appropriate setup skill first.

| v1 | v2 |
|---|---|
| ✅ **Met** — `ds-version` detects DS installation, Angular version, theme. `ds-impl` preflight validates environment. `ds-compose` validates workspace via `check-architecture.js`. | ✅ **Met** — `/sl-ds` router has state machine: `virgin` → forces `/sl-ds-setup` first. `sl-ds-setup` produces `codebase-analysis.json`. Router blocks downstream skills until setup completes. |

### R5 — Use only the design system — no custom component reimplementations

**Problem it solves:** AI was generating plain `<div>` + `<button>` structures for things that `sl-card`, `sl-button`, `sl-badge` etc. already handle. Resulted in inconsistent styling, missing accessibility behaviors, and components that don't benefit from DS updates.

**What it means:** If the DS has a component for a UI element, use it. Never reimplement an available DS component with custom markup. Use plain `<div>` only for layout containers that have no DS equivalent.

| v1 | v2 |
|---|---|
| ✅ **Met** — `ds-mapper` maps every Figma node to SLDS; DS1 quality metric "0 custom reimplementations of available sl-* components" enforced by `sdl-quality`. Unmapped nodes explicitly documented as gaps, not silently converted to divs. | ✅ **Met** — `generation-rules.md §4 rule SDS-3`: "layout containers = `<div>`, NOT `<sl-card>`." Hard gate blocks using DS component as layout wrapper. `component-map.json` classifies every Figma node as sl-ds-component / plain-div / html-text / asset-image. |

### R6 — Theme creation and token-only CSS

**Problem it solves:** Skills were either hardcoding hex values (`color: #0a6165`) or using SLDS generic token values that didn't match the project's Figma theme (SLDS generic = blue primary, Sanoma project = teal primary). Both are wrong.

**What it means:** Skills must (1) CREATE a project theme file that overrides SLDS base tokens with project-specific values (`--sl-color-foreground-primary-bold: #0a6165`), (2) generated component CSS uses ONLY DS token names (`var(--sl-color-foreground-primary-bold)`), never hardcoded values, (3) theme file is the single place to change the visual identity.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-version` detects active theme (`@sl-design-system/<theme>` import). `scss-design-system-pro` worker handles theming code. DS2/DS3/DS7/DS8 quality metrics enforce zero hardcoded colors/spacing/typography. But **no mechanism to generate a theme override file** from Figma variable values. | ❌ **Open** — `token-name-transform.md` establishes correct `--sl-*` naming. HARD GATE blocks legacy `--color-*` vars. But **theme override generator missing**: `sl-ds-tokens` does not compare `get_variable_defs` output against `light.css` and does not generate `sanoma-theme.css`. Generated code uses correct var names but resolves to wrong values (SLDS blue, not Sanoma teal). |

**What the fix looks like:**
```
sl-ds-tokens:
  1. get_variable_defs → actual resolved values for this Figma project
  2. Compare against SLDS light.css
  3. Where different → write apps/<scope>/src/styles/sanoma-theme.css:
       :root { --sl-color-foreground-primary-bold: #0a6165; }
  4. Components use var(--sl-*) — theme file provides correct values
```

### R7 — Figma caching and change detection

**Problem it solves:** Every run re-extracted all Figma data even when the design hadn't changed, burning API quota and adding minutes to generation time. There was also no way to detect that a design had changed since last run.

**What it means:** Cache all Figma extraction results keyed by `{file-id}@{lastModified}`. On subsequent runs, if Figma's `lastModified` hasn't changed, use the cache. Detect and surface when a new Figma version exists (compare cached lastModified vs current).

| v1 | v2 |
|---|---|
| ✅ **Met** — `ds-figma` caches by `{file-id}--{frame-id}@{lastModified}`. Cache lives in `.ds-cache/figma/`. Multi-screen dedup: same component across N screens fetched once. `--no-cache` flag for forced refresh. `ds-api` also caches SLDS API data per version in `.ds-cache/ds-api/{version}/`. | ✅ **Met** — `tokens-verified.json` is the Figma cache. Router reads `figmaLastModified` from `pipeline-state.json` and checks `figmaChangedSinceCache`. State: `completed-fresh` (no change) vs `completed-stale` (changed → `/sl-ds-update`). |

### R8 — Generation speed: target 1–2 min, maximum 10 min with visible progress

**Problem it solves:** The full pipeline was taking ~10 minutes in v1 (considered long) and up to 1 hour in later iterations. Iterative design-to-code workflows became impractical when a single screen took an hour.

**What it means:**
- **Target:** 1–2 minutes per screen (plan + generate + verify)
- **Acceptable:** up to 10 minutes **if the developer sees live progress** (step-by-step updates, not a spinner)
- **Unacceptable:** anything approaching 1 hour regardless of progress visibility

Achieved by: minimizing sequential AI calls, tight context windowing (sub-agents receive only what they need), parallel execution where possible, caching to skip already-done work, and reducing total skill count.

| v1 | v2 |
|---|---|
| ❌ **Not met** — 7-step ds-* pipeline + 7-phase sdl-master = 14 sequential stages. Full run at 35–150K tokens. sdl-master was ~10 min in early versions; adding quality pipeline pushed it further. Designed for thoroughness, not speed. | ⚠️ **Partial** — 15 skills, granular context per sub-agent. Model tier routing (Haiku/Sonnet/Opus). Skill count actively being reduced. Each skill prints progress updates. No benchmark confirming target. Standards context overflow (R15) adds latency. |

### R9 — LLM cost optimization: model tier routing

**Problem it solves:** Using the most expensive model (Opus) for simple state detection or intent matching burned unnecessary cost. A router choosing between Haiku/Sonnet/Opus based on task complexity reduces cost while maintaining quality.

**What it means:** Simple tasks (state detection, intent matching) → Haiku. Sub-task execution (component mapping, cluster detection) → Sonnet. Complex orchestration (full plan writing, SPEC generation) → Opus.

| v1 | v2 |
|---|---|
| ❌ **Not met** — No model tier routing defined. All agents run on the same model. Context windowing per BLOK saves tokens but cost per token is the same. | ✅ **Met** — Explicitly defined: Haiku = router/state detection, Sonnet = sub-agents (mapping/clustering/data-flow), Opus = orchestrator (PLAN.md generation, SPEC writing). |

**What it means:** A dedicated help skill answers DS component questions inline: prop names, slot names, event names, import paths, usage examples, known gotchas. Version-aware (answers reflect the exact installed DS version).

Warning policy (flags draft/preview components, breaking changes, missing Angular wrappers). Output includes: short answer + import/registration instructions + usage example + property/event/slot summary. | ✅ **Met** — `sl-ds-help`: queries `get_code_connect_map` for authoritative Code Connect data. Returns exact sl-* snippets as configured in the Figma DS library. Simpler than ds-docs but more authoritative on current API. |

**What it means:** Skills must support a short 4-step flow for single-component scope (tokens for that node only → plan for that component → implement → verify). Auto-detect when the Figma URL points to a COMPONENT node.

### R12 — Data/presentation encapsulation

**Problem it solves:** Generated components had hardcoded data inline (static strings, arrays in templates). Connecting a real data layer required rewriting the component, not just swapping the data source. This made generated code disposable rather than production-ready.

**What it means:** Generated code must separate smart containers (own state/service injection) from presentational leaves (receive data via `input.required<T>()`). Data layer swap should require only changing the smart container's service injection, not touching any presentational component.

| v1 | v2 |
|---|---|
| ✅ **Met** — `ds-compose` Step 2: strict SMART/DUMB classification. SMART = state-owning, service-injecting. DUMB = purely presentational, receives typed inputs only. Quality metric A7: "Separation of concerns — logic vs presentation vs state, 0 cross-concern leaks." Quality metric A1: "No service injection in presentational components." | ✅ **Met** — `sl-ds-plan` Step 5 (Data Layer Plan): smart container holds inline `signal<T>()` data and passes to leaves via `input.required<T>()`. Migration path documented: "replace inline signals with `inject(ServiceName)` returning `signal<T>` backed by HttpClient; leaves unchanged." |

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-mapper` maps Figma icon names to SLDS icon names using `knowledge/figma-to-slds-mapping.json`. `ds-api` includes icon registry data from CEM. ### R15 — Project standards compliance

**Problem it solves:** Generated code that violated Angular/SLDS standards (wrong change detection strategy, wrong SLDS import patterns, constructor injection instead of `inject()`) had to be manually corrected, negating the time savings.

**What it means:** Skills enforce Angular 21 patterns (standalone, signals, `inject()`, `@for/@if`, OnPush) and SLDS integration patterns (register.js, CUSTOM_ELEMENTS_SCHEMA) during generation. Standards live in `.agents-v2/standards/fe/`.

**Known unresolved problem:** The standards files are large and fill the LLM context window when loaded in full. This is an active tension between completeness and generation speed (see R8).

| v1 | v2 |
|---|---|

### R16 — DS versioning: handle DS version bumps

**Problem it solves:** When a new version of `@sl-design-system/*` is published, component APIs change (props renamed, slots removed, new variants). Generated code based on the old API breaks. There was no automated path to migrate existing generated code to the new DS version.

**What it means:** Skills must (1) detect the exact installed DS version, (2) compare it against the version used when code was generated, (3) identify breaking changes, (4) migrate generated code to the new API. **Original implementation note:** the DS was planned to publish bundled components to a GitHub repo that skills could pull directly — bypassing Nexus for CI/CD.

| v1 | v2 |
|---|---|
| ✅ **Met** — `ds-migrate`: dedicated migration orchestrator. Compares two version caches, identifies breaking changes via `CHANGELOG.md` diff, generates `IMPL_*.md` migration plan, executes via `sdl-master`. `ds-api` stores breaking changes in `.ds-cache/ds-api/{from}-to-{to}.json`. `ds-version` detects exact installed version from lockfile. | ❌ **Not met** — `sl-ds-setup` detects version but no migration skill. No version comparison. No breaking change detection. Manual DS upgrade requires re-running the full pipeline. |

### R17 — Full update cycle: Figma changes + skill/prompt updates + DS updates

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-audit` detects Figma drift (classifies changes: added/removed/renamed/property delta). `ds-impl --diff` re-runs only changed screens. `ds-migrate` handles DS version bumps. No mechanism for skill/prompt self-update. | ⚠️ **Partial** — `sl-ds-update` handles Figma changes (diff-aware, per-category: tokens / layout / structural / mixed). Router detects `completed-stale` state. No DS version migration. No skill self-update mechanism. |

### R20 — No circles: catch errors early, detect recurring failures

**Problem it solves:** The loop: generate → verify fails → generate again with the same plan → same failure. Nothing in the pipeline detected that the same error was recurring and escalated to the developer.

**What it means:** (1) Catch TypeScript/build errors immediately after generation (before saving/completing), not deferred to a separate verify step. (2) Track failure fingerprints across sessions — if the same error recurs, escalate instead of retrying. (3) Auto-repair loop with limits.

| v1 | v2 |
|---|---|
| ✅ **Specified** (never executed) — 5-guard loop protection: issue fingerprint (same file+line+type → UNFIXABLE), file state hash (no-op detection), cycle limit (max 3), regression detector (revert if test count drops), token budget (90K total, 30K/cycle). `sdl-gap-analysis` verifies each EXIT CRITERION via real shell exit code. | ❌ **Open** — `sl-ds-verify` has 3-retry build fix loop. **No TypeScript compilation check after generation** — type errors discovered late (only at verify step), not immediately after generation. **No failureHistory across sessions** — router does not detect recurring failures. |

### R21 — Resumability: continue after interruption

**Problem it solves:** A generation run for a complex screen can take many minutes. If the computer closes, internet drops, power fails, or the user closes the window mid-run, all progress is lost and must restart from scratch.

**What it means:** After every completed step, persist enough state to resume from that exact point on the next run. Resume must be transparent — same output as if the run had never been interrupted. No manual bookkeeping by the developer.

| v1 | v2 |
|---|---|
| ✅ **Specified** (never fully tested) — `pipeline-state.json` v2 with checksums per artifact, 7 resume validation rules (schema version, artifact existence, checksum, lock ownership, config snapshot). Three resume modes: `--resume`, `--force-resume`, `--restart`. Step-level checkpoints provide a recovery trail. | ❌ **Open** — `pipeline-state.json` records completed steps but `sl-ds-implement` does not read it to resume mid-phase. If a session is interrupted during Phase 2 of implement, the next run restarts Phase 2 from scratch. Step-level checkpoints exist but no formal resume protocol. |

### R22 — Multi-agent support (Claude, Copilot, other AI systems)

**Problem it solves:** Skills are currently designed for Claude Code specifically (using `AskUserQuestion`, `Agent` tool, slash commands). Other AI coding assistants (GitHub Copilot, Cursor, etc.) cannot use the same skills without significant rework.

**What it means:** Skill format and invocation patterns should be compatible with multiple AI systems, or clearly document the adaptation needed. The instruction format, tool contracts, and MCP integrations should be abstracted enough to port to other AI environments.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-*` agents are plain Markdown files that can be passed as system prompts to any AI model. No `AskUserQuestion` or slash command dependencies. Portable in principle. `sdl-*` workers execute shell commands which are also AI-agnostic. | ❌ **Not portable** — Skills use Claude-specific features: `AskUserQuestion` tool, `Agent` tool with `subagent_type`, slash command invocation (`/sl-ds-*`), MCP tool calls (`mcp__claude_ai_Figma__*`). ### R23 — Multi-framework support (Angular, Lit, Web Components, others)

**What it means:** Skills should generate correct code for the target framework detected in the project, or allow explicit override. Angular-specific patterns (standalone components, `inject()`, signal inputs) should be isolated from framework-agnostic logic (SLDS component mapping, token extraction, layout planning).

| v1 | v2 |

Adding another framework requires a new `generation-rules.md` variant and significant SKILL.md updates. |

### R24 — Multi-ecosystem support (NX, plain Angular CLI, others)

### R25 — RWD (Responsive Web Design) by default

**Problem it solves:** Figma designs are typically at 1440px desktop width. Generated components used fixed pixel values from Figma (e.g. `width: 429px`), producing components that don't scale on mobile or tablet.

**What it means:** All generated CSS must produce fluid, responsive layouts by default. Fixed Figma pixel values must be translated to: percentages, `fr` units (CSS Grid), `clamp()`, or responsive breakpoints. Components must scale correctly from mobile (320px) to desktop (1440px+) without horizontal scroll or overflow.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — `ds-figma` Pass 3 extracts `{ responsive? }` flag from auto-layout containers. `ds-compose` uses Figma ratios to generate `grid-template-columns: minmax(0, Xfr) minmax(0, Yfr)`. Quality metric VF4 checks "flex/grid with correct direction, gap token, and alignment." But no explicit RWD breakpoint generation step. | ❌ **Open** — `sl-ds-plan` captures Figma absolute positions (`x, y, w, h`) in PLAN.md and uses `position_strategy: flex-grid`. But no step converts Figma fixed widths to responsive units. No breakpoint generation. Verified as broken in Desktop-7 implementation — see "Known Unresolved Issues." |

### R26 — Maximum automation; ask rather than assume

**Problem it solves:** Skills were either too silent (making wrong assumptions without asking) or too chatty (asking unnecessary questions). The right balance is: automate everything that can be determined from the codebase/Figma/DS, but always ask — with concrete suggestions — when there is genuine ambiguity or a conflict.

**What it means:** Default behavior is fully automatic — no prompts unless needed. When a prompt IS needed, always offer 2–4 concrete options with descriptions. Never ask open-ended "what do you want?" questions. The developer should always be able to pick an option or type a custom answer, not write an essay.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — Confidence threshold (< 40) triggers pause. Approval mode serializes questions. But questions only emerge reactively from detected ambiguity. No proactive structured options. Open-ended prompts possible. | ✅ **Met** — `AskUserQuestion` with 2–4 labeled options + descriptions used at every decision point. Every option has a recommended choice marked (⭐). User can always select "Other" for free-form input. Default path is fully automatic; questions only on genuine ambiguity or architect choices. |

### R27 — Hand-holding with concrete suggestions (not open questions)

**Problem it solves:** "What architecture should I use?" is an unhelpful question — the developer wants a recommendation they can accept or adjust, not a blank form to fill. Skills should lead the developer through decisions with concrete, reasoned options.

**What it means:** Every question must include at least one recommended option (marked as recommended), a description of what each option means in practice, and the tradeoff. The developer picks from options or overrides. The skill never waits for the developer to figure out what to type.

_Note: This refines R18 (structured questions) and R19 (hand-holding) — they covered the mechanism, this requirement covers the quality of the guidance itself._

| v1 | v2 |
|---|---|
| ❌ **Not met** — Questions emerge from confidence drops, not from proactive guidance. When a question is asked, it does not include pre-filled recommended options with tradeoffs. | ✅ **Met** — `AskUserQuestion` format requires: `label` (the option), `description` (what it means + tradeoff), one option marked as "⭐ Recommended." Skills explicitly state the reasoning behind the recommendation. This pattern is enforced across all 15 skills via `_shared/questions-format.md`. |

### R28 — Context management: auto-split when context is too large

**Problem it solves:** Complex screens with 30+ components exceed LLM context limits mid-generation, causing truncated output, silent failures, or hallucinations. The developer had no visibility into this and no recourse other than restarting.

**What it means:** Skills must track running context usage and proactively split work before hitting limits. A screen with 20 components that would overflow context in one pass must automatically be divided into 2–3 phases, each fitting comfortably within context limits. Progress must be visible to the developer.

| v1 | v2 |
|---|---|
| ⚠️ **Partial** — Token budget defined per agent (e.g. ds-mapper 2–3K, ds-impl 35–150K). DS_AGENTS_ARCHITECTURE §13 has a complete per-scenario budget table. Overflow in Step 6 (SPEC generation for LARGE scope) is identified as a known failure mode: last components get incomplete specs. No automatic split mechanism specified. | ⚠️ **Partial** — `sl-ds-plan` uses SMALL/MEDIUM/LARGE scope tiers (based on `nodeCount` from `scope.json`) to size the plan. LARGE scope triggers multi-phase PLAN.md. `sl-ds-implement` sub-agents receive only their phase section (not the full plan). But no runtime context monitoring during generation, no auto-split when a phase grows unexpectedly large. |

### R29 — Shared document format: all skills read/write compatible documents

**Problem it solves:** Different skills wrote to incompatible document formats — one skill produced `step-1-interpret.json`, another expected `component-tree.json` in a different schema. Skills from different sessions or run orders broke each other's outputs.

**What it means:** All cache artifacts, PLAN.md format, pipeline state, and decision documents must follow documented, versioned schemas. If Skill A produces an artifact, Skill B must be able to read it without knowing which version of Skill A wrote it. Schema versions must be checked at pre-flight.

| v1 | v2 |
|---|---|
| ✅ **Met** — DS_AGENTS_ARCHITECTURE Appendix B defines artifact schemas for every step output: `component-tree.json`, `slds-tree.json`, `composition-plan.json`, `quality-report.json`. `pipeline-state.json` v2 has a defined schema version field. State Resume hardening (§16.5) includes schema version match as one of 7 resume validation rules. | ⚠️ **Partial** — `_shared/cache-schema.md` defines the PLAN.md frontmatter schema (v2). `sl-ds-implement` pre-flight rejects plans without `plan_schema: "v2"`. But intermediate artifacts (`codebase-analysis.json`, `component-map.json`, `clusters.json`, `data-plan.json`) have informal schemas — no versioning, no pre-flight validation between skills. |

### R30 — Accessibility: WCAG compliance in all generated code

**Problem it solves:** Generated components had no ARIA labels, no keyboard navigation, no focus management, no color contrast checks. Screen readers couldn't use generated UIs. This was a legal and UX compliance failure.

**What it means:** All generated code must meet WCAG 2.2 AA by default (configurable to A or AAA). This includes: semantic HTML, ARIA roles/labels on interactive elements, keyboard navigation (Tab, Enter, Escape), focus management, color contrast (4.5:1 body, 3:1 large text), live regions for dynamic content.

| v1 | v2 |
|---|---|
| ✅ **Met** — 5 dedicated `a11y-*` agents: `a11y-review` (design-time accessibility audit on Figma tree), `a11y-impl` (embeds ARIA and keyboard behaviors during code generation), `a11y-audit` (post-generation WCAG check via axe-core), `a11y-navigator` (keyboard flow analysis), `a11y-test` (automated a11y test generation). Quality group Accessibility = 18% weight. Standard configurable in `.ds-config.yaml` (`accessibility.standard: WCAG22-AA`). | ❌ **Not addressed** — No a11y skill, no a11y check in `sl-ds-verify`, no ARIA insertion in `sl-ds-implement`. `generation-rules.md §4 rule 7` states "aria-label on icon-only buttons — Mandatory" but this is the only a11y rule. No axe-core integration, no keyboard nav testing. |

### R31 — Accessibility help skill: analyze, guide, answer questions

**Problem it solves:** Developers implementing accessibility had no support — they had to consult external docs, make judgment calls, and often got it wrong. There was no way to ask "is this component accessible?" or "what do I need for WCAG AA on this screen?"

**What it means:** A dedicated accessibility help skill that can: (1) analyze an existing component or screen and identify accessibility gaps, (2) provide specific guidelines for fixing each gap, (3) answer questions about accessibility approaches ("how should I handle focus trap in this modal?"), (4) support different conformance levels (A, AA, AAA) and output guidance specific to the requested level.

| v1 | v2 |
|---|---|
| ✅ **Met** — `a11y-audit` analyzes components against WCAG 2.2 AA (axe-core). `a11y-navigator` analyzes keyboard navigation flows. `ds-docs` can answer DS-specific accessibility questions (component ARIA contract). Configurable standard: WCAG22-AA, WCAG22-A, WCAG22-AAA, WCAG21-AA. | ❌ **Not addressed** — No dedicated accessibility help skill. `sl-ds-help` answers DS component questions but has no accessibility analysis capability. No way to audit an existing component or get accessibility guidance for a new screen. |

## Architecture

### v1 — Two-layer system

```
Developer calls: ds-impl [figmaUrl] [projectRoot]
         │
         ▼
7-step ds-* pipeline:
  Step 1  ds-figma          3-pass Figma extraction (Structure/Components/Layout)
  Step 2  ds-mapper         CEM-based SLDS mapping + ds-api + a11y-review
  Step 3  ds-compose        Inline architecture plan (smart/dumb, NX layers, routes)
  Step 4  angular-specialist  Angular 21 code generation
  Step 5  sdl-quality        Real nx lint/test + web-codegen-scorer
         │
         ├── SIMPLE → ds-impl integrates directly
         │
         └── COMPLEX → IMPL_*.md → sdl-master (7 phases):
                         Phase 0  Plan scoring + advisory agents
                         Phase 1  sdl-impl-orchestrator → per-BLOK routing → specialist workers
                                  (intra-BLOK smoke test after every BLOK)
                         Phase 2  sdl-gap-analysis (shell EXIT CRITERION verification)
                         Phase 3  sdl-quality + 4 specialist agents
                         Phase 4  sdl-verification (unit + Storybook + E2E + DevTools MCP)
                         Phase 5  sdl-cicd-orchestrator
                         Phase 6  sdl-retrospective
```

### v2 — Single-layer skills

```
Developer invokes: /sl-ds [Figma URL]
         │
         ▼
sl-ds Router (Haiku) → reads state, matches intent
         │
         ▼
sl-ds-setup      → codebase-analysis.json
sl-ds-tokens     → tokens-verified.json (get_design_context + verify vs light.css)
sl-ds-plan       → PLAN.md (cluster detection + data layer + per-component SPEC)
sl-ds-implement  → code from PLAN.md (Sonnet sub-agents per component)
sl-ds-verify     → nx build + pixelmatch + composite fidelity score
```

## Key Factual Differences

### SLDS API resolution

**v1:** Fetches TypeScript source from `raw.githubusercontent.com/sl-design-system/...`, parses with ts-morph. Accuracy ~90%. Augmented by `knowledge/figma-to-slds-mapping.json` (curated 4-column table: Figma name patterns → SLDS tag + property map + confidence). Token budget: 2–3K.

**v2:** Calls `get_code_connect_map` (Figma MCP). Returns exact sl-* snippets as published by the SLDS team in Code Connect. Authoritative. No parsing needed.

### Quality verification

**v1 (`sdl-quality`):** Runs actual shell commands: `nx affected --target=lint`, `npx web-codegen-scorer >80`, Angular CLI MCP (`get_best_practices`, `modernize`), `nx affected --target=test`. Per-BLOK smoke test after every code change. EXIT CRITERION bash blocks verified by shell exit code.

**v2 (`sl-ds-verify`):** Runs `nx build` + pixelmatch against Figma screenshot + composite Design Fidelity Score. No per-component smoke test during generation.

### State persistence

**v1:** Three levels: `pipeline-state.json` (run-level, checksums, 7 resume rules), `SDL_STATE_${SPRINT}.md` (sprint-level, phase state), `CHECKPOINT_BLOK.md` (per-BLOK). Lock file with heartbeat.

**v2:** Single `pipeline-state.json` (step list, figmaLastModified, current screen). No checksums, no crash recovery, no per-BLOK checkpoints.
