# DS Mock — Generate Realistic Mock Data From Node Tree

## Purpose

`/sl-ds-plan` decides a data approach (Signal Store / service-with-mock / static); `/sl-ds-implement` writes the service/store skeleton — but the actual mock array is left as a placeholder (`groups: []`). The user fills it in by hand, which means each new screen requires manual mock-data invention. This skill infers realistic shapes from Figma text nodes (group cards with student counts, dashboard insights with progress percentages, etc.) and populates the service. Idempotent: re-running adds missing fields without overwriting hand-edits.

## When to use

- `/sl-ds-implement` just completed; `/sl-ds-plan` picked `service-mock` or `signal-store` data approach
- User explicitly says "generate mocks", "fill in seed data", "wygeneruj mocki"
- New screen added to an existing project — its service needs initial mock data before HTTP integration

## When NOT to use

- Data approach is `static` (`/sl-ds-plan` chose to inline data in page component — there's no service to mock)
- `/sl-ds-implement` hasn't run yet — service file doesn't exist
- Production data integration is the actual goal — this skill is for development-time mocks ONLY; never write to real-data endpoints

## Preconditions

| Required artifact | If missing |
|---|---|
| `.sl-ds-config.yaml` | STOP per [`../_shared/refusal-protocol.md`](../_shared/refusal-protocol.md) §4.7 (producer: `/sl-ds-setup`) |
| `.sl-ds-cache/sl-ds-impl/node-tree.json` | STOP per §4.7 (producer: `/sl-ds-tokens`) |
| `.sl-ds-cache/sl-ds-impl/component-map.json` | STOP per §4.7 (producer: `/sl-ds-plan`) |
| `.sl-ds-cache/sl-ds-impl/architecture.json` | STOP per §4.7 (producer: `/sl-ds-plan`) |
| Service/store file generated by `/sl-ds-implement` | STOP per §4.7 — re-run `/sl-ds-implement` first |

Plus: `architecture.json.dataApproach` MUST be `service-mock` or `signal-store`. If `static` → refuse with explanation that there's no service to populate.

## Inputs

**`$ARGUMENTS` (all optional):**

| Field | Description |
|---|---|
| `--rows=<N>` | How many mock items per collection (default: 10 for groups/items; 24 for students; 6 for actions) |
| `--locale=pl\|en` | Language for human-readable mock strings (default: detect from `.sl-ds-config.yaml` → `i18n.library` or fall back to `en`) |
| `--no-fixtures` | Skip generating test fixtures alongside service mocks |
| `--force` | Overwrite existing hand-tuned values (default: idempotent — preserve hand-edits, add only missing fields) |

## Workflow

### Step 1: Identify service/store file + current shape

**Executor:** orchestrator on **sonnet**

From `architecture.json.componentTree`, find the file with `kind: "service"` or `kind: "store"`. Read it. Parse the model interface (e.g. `interface DashboardData { groups: DashboardGroup[]; }`).

If the file's mock-data section already contains non-trivial values (more than empty arrays / null literals), set `existingMocks = true`. Idempotent mode (default) PRESERVES these and only adds missing fields per new model additions.

### Step 2: Spawn shape-inferrer sub-agent

**Executor:** `Agent(subagent_type: "general-purpose", model: "sonnet")` — clean context.

**Sub-agent inputs:** node-tree.json path, component-map.json path, model interface from Step 1, `--locale` value, reference to [`references/shape-inference.md`](references/shape-inference.md).

**Sub-agent task:** scan Figma TEXT nodes whose content suggests data (e.g. "24 students", "Class 3A", "75% complete"), group by likely-collection (sibling nodes with same parent + similar names like `group-card-1`, `group-card-2`), infer field types per collection (string for names, number for counts, percentage 0-1 for progress).

**Sub-agent output schema** (inline contract):

```json
{
  "schemaVersion": "1.2.0",
  "producedBy": "sl-ds-mock/shape-inferrer",
  "producedAt": "<iso>",
  "collections": [
    {
      "modelName": "DashboardGroup",
      "inferredFrom": ["node 1:201 'group-card-1'", "node 1:202 'group-card-2'", "node 1:203 'group-card-3'"],
      "fieldShapes": {
        "id": { "kind": "uuid" },
        "name": { "kind": "string", "examples": ["Class 3A", "Class 3B", "Class 4A"], "pattern": "Class <number><letter>" },
        "studentCount": { "kind": "number", "range": [18, 28], "examples": [24, 21, 26] },
        "progress": { "kind": "percentage", "range": [0.0, 1.0], "examples": [0.75, 0.43, 0.91] },
        "lastActivity": { "kind": "date-recent", "range": "30d" }
      },
      "rowCount": 3,
      "confidence": "high"
    }
  ],
  "unmappedTextNodes": [
    { "nodeId": "1:300", "text": "Welcome back, Marcin", "reason": "Greeting — not a collection item" }
  ],
  "appliedRules": ["DATA-1", "DATA-3", "STATE-3"]
}
```

### Step 3: Generate mock arrays

**Executor:** orchestrator on **sonnet**

For each collection in the sub-agent output:

1. Build an array of `--rows` items (or `rowCount` from shape if non-empty Figma sample exists — use the Figma examples as first N, generate the rest from `kind` + `range` + `pattern`)
2. Field generation rules in [`references/shape-inference.md`](references/shape-inference.md) §3 (id → crypto.randomUUID; name → pattern-based or faker-style locale-aware; number → range-uniform; date-recent → now() - random(0, 30 days); etc.)
3. Inject into service/store file at the marked location

Idempotent merge (default — no `--force`):
- For fields ALREADY populated with non-trivial values → preserve
- For fields with `null` / `undefined` / `[]` / `''` → fill with generated value
- For fields missing entirely → add to each item

### Step 4: Generate test fixtures (unless --no-fixtures)

**Executor:** orchestrator on **sonnet**

Per `architecture.componentTree`, the test file pattern is `<component>.spec.ts` alongside source. For each collection:

- Edge-state fixtures: empty `[]`, single item, max items
- Boundary fixtures: min/max numeric values, longest string

Write to `<component>.fixtures.ts` if the project's testing convention uses separate fixtures files (detect from `codebase-analysis.json` or default to inline in `.spec.ts`).

### Step 5: Summary

```text
> ✅ Mock data generated
>
> | Collection | Rows | Existing preserved | Fields added | Fixtures |
> |---|---|---|---|---|
> | DashboardGroup | 10 | 3 (had names from Figma) | 4 fields | 3 fixture variants |
> | DashboardInsight | 6 | 0 | all fields | 2 fixture variants |
>
> Files modified:
> - features/.../teacher-dashboard.store.ts (mocks expanded)
> - features/.../teacher-dashboard.fixtures.ts (NEW)
>
> Next: `/sl-ds-verify` to confirm build still passes with new mocks
```

Write `.sl-ds-cache/sl-ds-impl/mock-result.json` with inferred shapes + applied rules + preserved-vs-added counts.

## Outputs

| Path | Purpose |
|---|---|
| `.sl-ds-cache/sl-ds-impl/mock-result.json` | Inferred shapes + audit trail |
| Modified `<service-or-store>.ts` | Mock arrays populated |
| `<component>.fixtures.ts` (new or modified) | Test fixtures (unless `--no-fixtures`) |

## Hard gates

- `architecture.dataApproach === "static"` → STOP. Surface: *"No service to populate — data is inline in the page component per architecture decision. Edit the page component directly or change data approach via `/sl-ds-plan --force`."*
- Service file doesn't have the expected mock-data marker / empty array pattern → STOP. *"Generated service file doesn't match expected shape (manual rewrite?). Cannot safely inject mocks. Use `--force` to overwrite the data section, OR populate by hand."*
- `--force` would overwrite hand-edited values → ASK before doing it (don't silently destroy work).
- Shape-inferrer sub-agent returns no collections (Figma has no data-shaped text) → STOP cleanly. *"No data collections inferable from this Figma file. The screen may not need mocks — only data-bound screens benefit from this skill."*

## Resume

Resume per [`../_shared/resume-discipline.md`](../_shared/resume-discipline.md). Progress: `.sl-ds-cache/sl-ds-mock/progress.json`. Checkpointed steps: Step 2 (per-collection shape inference), Step 3 (per-collection mock array generation). Idempotent merge (Step 3 default) makes resume safe — re-running fills only missing fields. Manual fallback table (if `progress.json` missing or corrupt):

| State on disk | Resume hint |
|---|---|
| `mock-result.json` exists + matches `architecture.componentTree` hash | Already done; print summary, EXIT |
| Service file has partial mocks (`name` filled but `studentCount` empty) | Step 3 idempotent merge — fill missing only |
| Nothing | Step 1 (fresh) |
